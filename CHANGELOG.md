# Changelog

Tags `vX.Y.Z` version the repository. The Go module
`github.com/truvity/grun/boundary` is versioned by its own tags,
`boundary/vX.Y.Z`.

## Unreleased

- **Trim the default memory: `fg-small` 1 vCPU / 6 GB to 1 / 4, `fg-medium` 2 / 14 to 2 / 8, `fg-large` 4 / 24 to 4 / 12** (runner-sizing decisions of 2026-10-24, SZ2 B). Memory was about 39 % of the Fargate bill while jobs used about 14 % of the GB-seconds paid for; the largest working set measured on 4 vCPU is 7.2 GB, on 2 vCPU 5.8 GB. vCPU and the ephemeral storage are unchanged. **Do not deploy this before the heavy jobs have been moved to bigger sizes through the central mapping in ci-workflows: a job that needs more than the new limit is killed by the OOM killer, which reads as a hang or a lost runner, not as an error.** Task definitions change (a new revision per shape and organisation); the image is not rebuilt. Tests: the three shapes' memory.
- **Add the shapes `fg-xsmall` (0.5 vCPU / 1 GB, 21 GiB), `fg-medium-spot` (2 / 8 on Fargate Spot) and `fg-xlarge` (8 / 16, 100 GiB, on-demand; `XLARGE_SHAPE` in `config.ts`) to the defaults, and `shapes[].spot`** (runner-sizing decisions of 2026-10-24: SZ1 A, SZ10 A, SZ13 B). Purely additive: the three existing shapes keep their sizes and their providers, task definitions and roles are untouched; each organisation gains three providers and three task roles (`<stack>-<org>-fg-xsmall-task`, `-fg-medium-spot-task`, `-fg-xlarge-task`, which the telemetry issuer must admit like the others). `spot: true` runs a shape on the `FARGATE_SPOT` capacity provider (cdk-github-runners 0.17's `spot` option; the cluster already has both providers). **A Spot interruption fails the job it runs: GitHub does not retry it and the requeue (`runner.requeue`) covers only a job that never got a runner**, so a Spot job is recovered by a rerun; use it for the Renovate fleet first, never on a stable tier. A warm pool on a Spot shape is refused at load. Tests: the six shapes and their task definitions, the capacity provider per shape, the Spot flag from the file, the warm-pool refusal, the selector's labels.
- **grun-agent: time at the CPU cap, peak ephemeral disk, the job's display name** (SZ11 A). `grun.job.peak` gains `cpu_at_cap_s`, `cpu_measured_s`, `cpu_at_cap_fraction` (the CPU rate over a sampling interval at 95 % or more of the task's vCPU, and the seconds measured), `peak_disk_mib`, `disk_start_mib`, `disk_total_mib` (`statfs` of `/`), `job_name` (the job's name with its matrix values, read from the Worker log's job message; absent when not there) and `cpu_source`; the gauges `grun_job_cpu_at_cap_seconds` and `grun_job_disk_peak_bytes` and the `::notice::` line follow. Fields are only added: every existing field and gauge keeps its name and meaning. A job shorter than the task stats' refresh (about 6 s) reported CPU 0; the agent now falls back on the runner container's cgroup CPU time over the job (`cpu_source=cgroup`). The image is rebuilt (the agent is in it). Tests: the seconds at the cap (the 95 % boundary, an unknown vCPU, a cached reading), the cgroup fallback and its readers, the disk figures, the name from a Worker log, the event's fields.
- **Add the requeue function and `runner.requeue` (default on).** GitHub sends a job's queued webhook once and the idle reaper removes a runner that has not been handed a job in time, so the last jobs of a matrix with `max-parallel`, runnable only after their runners were reaped, stayed queued until cancelled. Every five minutes a Lambda looks at the runs of which a runner of this stack ended without a job (aborted `IdleRunner`) or failed, in the last 30 minutes, reads each run's jobs as the organisation's App, and starts one runner per still-queued job of the same label set less the runners still running for the run, through the same state machine and with the webhook's input. It skips completed runs, jobs queued for more than six hours and starts beyond the task cap, and alarms after three failed rounds. Tests: the plan for the max-parallel case, the running runners counted, completed runs, label sets and age, one GitHub read per run, the names, the configuration; in the stack the function, its schedule, its permissions and `runner.requeue: false`.
- **Add grun-agent and `telemetry`.** The runner image carries `agent/grun-agent.ts`, bundled at synth time (esbuild, one CommonJS file with the STS client) to `/opt/grun/grun-agent.js` and run by the runner's own Node from cdk-github-runners' user job hooks. Per job it samples the ECS task stats every few seconds and prints the peaks (memory with and without page cache, peak and average CPU, the task's size and the job's duration) as a `::notice::` line; it reads the warning, error and critical records the runner writes to `_diag`. With `telemetry` (`otlpEndpoint`, `issuerUrl`, optional `stsAudience`, `otlpAudience`, `sampleSeconds`) it sends the records as OTLP logs and the peaks as OTLP metrics plus one log event, with an access token it trades (RFC 8693) for the task role's web identity token; the task roles then get `sts:GetWebIdentityToken` for that audience only (ES384, at most 300 s). Every task gets `GRUN_TIER`, `GRUN_ORG`, `GRUN_SIZE` and `GRUN_REGION`, and with telemetry the `GRUN_OTLP_*` settings. The agent is fail-open and the hooks never fail a job. The image is rebuilt (new components). Tests: the stats arithmetic, the diagnostic log reader (levels, continuation lines, appends, bounds), the OTLP bodies, the notice line, the bundle; in the stack the components, the environment and the IAM statement with and without telemetry.
- **The runner's diagnostic trace is off stdout; add `runner.traceToStdout` and `runner.logRetentionDays`.** Every task now sets `ACTIONS_RUNNER_PRINT_LOG_TO_STDOUT=false`. The upstream runner image sets it to 1, so the runner listener's and worker's whole trace (`[WORKER … INFO ActionManifestManagerLegacy]` and the like) reached stdout and the task's CloudWatch log group, which was nearly all of what those groups ingested; the job's own output lives in GitHub, and the runner keeps writing the same trace to `_diag` in the task (where cdk-github-runners reads the job's result). The runner's terminal output (start-up, `Running job`, `Job … completed with result`, its error lines) and the `CDKGHR` lines stay on stdout. `runner.traceToStdout: true` restores the old behaviour. `runner.logRetentionDays` (the CloudWatch values; absent: `logRetentionDays`) sets the retention of the runner tasks' log groups alone; the orchestration functions, the state machine and the image builder keep `logRetentionDays`. Both are task definition changes, so a `cdk deploy` is enough and the image is not rebuilt. Tests: the variable on every task, false by default and true when asked; the task groups follow `runner.logRetentionDays` and every other group `logRetentionDays`; the schema refuses other values; the variable cannot also be an SSM secret.
- **Add `runnerEnvironment.mavenRegistry` and `runnerEnvironment.gradleBuildCache`.** The task environment `CI_RUNNER_MAVEN_REGISTRY` (the base of a Maven pull-through cache, one path per upstream: `<base>/central`, `/google`, `/gradle-plugins`) and `CI_RUNNER_GRADLE_BUILD_CACHE` (the URL of Gradle's remote build cache, HTTP protocol). ci-plane's cache-redirect serves both (its Maven and opt-in build cache front-ends, each at the root of a name of its own), and the shared `setup-devbox` step of truvity/ci-actions probes each, exports `CI_MAVEN_REGISTRY` / `CI_GRADLE_BUILD_CACHE` and installs a Gradle init script that points the build's declared repositories at the cache and registers the build cache; a cache that does not answer is a warning, never a failed job. Without these keys the Gradle builds of the runners download their dependencies from the public repositories and recompile everything, every time. The build cache is writable by whoever can reach it, so name the cache of this stack's own environment: each tier then reads only what its own jobs wrote (the estate gives the preview and the stable tier separate installations and buckets). A stack may still set `mavenRegistry` alone. Both are task environment, so a `cdk deploy` is enough and the image is not rebuilt. The schema takes an `http(s)` URL without whitespace. Tests: the variables are on the tasks when the keys are set and absent when not, and the schema accepts URLs and refuses a space, a newline, another scheme and an empty value.
- **Add `runner.idleTimeoutMinutes`.** The `idleTimeout` of cdk-github-runners, in minutes (integer, at least 1; absent: the library's 5). The idle reaper stops a runner that is registered, not busy and has been registered longer than this (measured from registration), and removes it from GitHub; it never stops a busy runner, one that has not registered yet, or a warm runner. A runner started for a job GitHub then cancelled or gave to another runner now disappears sooner, which shrinks the window in which it can serve a later job. The value reaches the webhook Lambda (`IDLE_TIMEOUT_SECONDS`) and the state machine default. Tests: the value is in the webhook environment of every organisation and in the state machine, and the library default (300 seconds) when the key is absent; the schema refuses 0, fractions and strings.
- **Add `orgs[].allow`, the webhook allow-list of the provider selector.** A non-empty list of `{repository: owner/name, workflows?: [names], refs?: [globs]}`. Before routing and capacity the selector refuses a job whose repository is not listed (case-insensitive), whose workflow name is not one of an entry's `workflows` (exact), or whose `head_branch` matches none of its `refs` (`*` matches any characters including `/`): no provider is returned, no capacity is spent, and one `Grun` / `AllowRefused` metric is logged (dimension `Stack`; organisation, repository, workflow and ref as properties). No alarm. An organisation without `allow` is unrestricted; once any organisation has one, a job from a login that is not in the file is refused. The lists reach the Lambda as one JSON variable, `ALLOW_LIST`, keyed by organisation login (`null` for an organisation without a list); a malformed value makes the Lambda fail at start. The config check refuses a repository of another owner than its organisation. Warm runners bypass the selector and are not covered. Tests: the allow matrix (repository, workflow, ref glob, no list, unknown organisation, metric, capacity not consulted), the strict parser, the schema, and the variable in the synthesized Lambda.
- **Add `runnerEnvironment.goCacheBucket`, `goCacheRegion` and `buildxCache`.** The tasks export `CI_RUNNER_GOCACHE_S3_BUCKET`, `CI_RUNNER_GOCACHE_S3_REGION` and `CI_RUNNER_BUILDX_CACHE`, the runner's own cache bucket and BuildKit cache reference. The shared CI actions prefer a runner value over the caller's organisation variable (as for `CI_RUNNER_GOPROXY`), so two tiers in one organisation (preview and stable) each use the bucket and registry cache of their own account while the organisation variable names one. It is task environment, so a `cdk deploy` is enough. The schema checks the shape of each (a bucket name, a region, a registry reference without a tag or a space); `goCacheRegion` without `goCacheBucket` is refused at load. Tests: the three variables are on the tasks when set and absent when not; the schema accepts and refuses the shapes; the region needs the bucket.
- **Add `runnerEnvironment.nixSubstituter`.** The URL of a Nix binary cache in front of cache.nixos.org (ci-plane's cache-redirect serves one under `/nix`). Set, every task exports `NIX_CONFIG` with `substituters = <url> https://cache.nixos.org/` and `connect-timeout = 5`: the estate's cache first, the upstream as the automatic fallback. Without it the Fargate runners fetched every store path of a devbox closure from cache.nixos.org, while the ARC runners got their cache from the pod's `NIX_CONFIG`. It is task environment, so a `cdk deploy` is enough and the image is not rebuilt: the image's nix is a single-user install owned by the runner user (no daemon, so no trusted-substituters question), and `NIX_CONFIG` is read after its nix.conf, which lists only the upstream. The cache serves the upstream's signed narinfos verbatim, so Nix's default trusted key verifies them and no `trusted-public-keys` is added. The schema takes an `http(s)` URL without whitespace, so the value cannot add a line to the Nix configuration. Tests: the variable is on the tasks when the key is set and absent when not; the schema accepts URLs and refuses a space, a newline, another scheme and an empty value.
- **Fix: Node trusts the private CA on the runners.** With `runnerImage.extraCertificates` set, every task now exports `NODE_EXTRA_CA_CERTS=/etc/ssl/certs/ca-certificates.crt`, the bundle `update-ca-certificates` rebuilds on the image. curl and git read the system store, but Node (installed by proto or devbox, not the system one) does not, so `yarn install` against `CI_RUNNER_NPM_REGISTRY` failed with `unable to get local issuer certificate`; the ARC runners exported the same variable. It is task environment, so a `cdk deploy` is enough and the image is not rebuilt. `trust-form/wallet#129` can drop `NODE_USE_SYSTEM_CA=1` once this is live. Test: the variable is on the tasks with a CA configured and absent without one.
- **Fix: a failed runner image build alerts through EventBridge, not CodeStar Notifications.** The library's `failedImageBuildsTopic` is an `AWS::CodeStarNotifications::NotificationRule`, whose creation races that service's service-linked role on a fresh account ("Invalid request provided: AWS::CodeStarNotifications::NotificationRule") and failed the first deploy into one. The stack now has an EventBridge rule on the image builder's CodeBuild project (`CodeBuild Build State Change`, `FAILED`, `FAULT` or `TIMED_OUT`; a stopped build is somebody's decision) that publishes a readable message (project, build id, status, log link) to the alerts topic, which now allows `events.amazonaws.com` to publish. This replaces the second topic (`Failed Runner Image Builds`), its email subscriptions (one confirmation mail per address instead of two) and the unused AWS Image Builder filter function the library added with it. The template has no CodeStar Notifications rule any more; the Deploy boundary still allows the service-linked role and can drop it in a later `boundary/v*` release.
- **Add `orgs[].runnerGroup`.** The GitHub runner group an organisation's runners register in (the library's provider `group`); absent, the organisation's default group, as before. The group's repository access then limits which repositories the runners serve, which is how a tier is piloted on one repository. The group must exist in GitHub before the first job. Tests: the schema, and the organisation's state machine names the group while another organisation's does not.
- README: "Runner groups and labels" says why two stacks in one organisation need shape labels of their own (the labels are the only routing between them) and how the group and the App's installation limit a tier.
- **Fix: the daily budget no longer asks for a forecast.** AWS refuses a `DAILY` budget with a `FORECASTED` notification at create time ("DAILY budget only supports notification type as ACTUAL"), which `cdk synth` cannot see; the first deploy failed there. `grun-<env>-daily` now notifies at 80 % and 100 % of the actual spend only. Two ordering fixes ride with it: the budget is created after the topic policy that lets Budgets publish (Budgets checks it at create time, and the budget only referenced the topic), and before the API Gateway custom domains, so a budget that is rejected fails while nothing slow exists. Before, the rollback met mutual TLS domains that were still updating and could not delete them ("There is already an update in progress for the domain"), leaving the stack in `ROLLBACK_FAILED`.
- **Config: two more create-time rules checked at load.** A shape's memory must go with its vCPU as Fargate lists them (ECS refuses the task definition otherwise), and a webhook certificate must be in the stack's region and the domain name a lowercase DNS name (API Gateway refuses the regional custom domain otherwise).
- Tests for rules AWS enforces at create time and `cdk synth` does not: no `FORECASTED` on a `DAILY` budget, the Budgets notification and subscriber limits, the budget's dependencies, the mutual TLS domain (regional, TLS 1.2, truststore, base path mapping), email subscriptions, the Arm CodeBuild compute type, log retention values (and every value the schema allows), DynamoDB billing mode, queue visibility timeout against the function timeout, alarm datapoints, and the 4 KB Lambda environment.
- **Add `cdk.qualifier`.** The CDK qualifier of the bootstrap the stack deploys through, set as the `DefaultStackSynthesizer` qualifier of the stack: its assets, publishing roles and bootstrap-version parameter become `cdk-<qualifier>-*` and `/cdk-bootstrap/<qualifier>/version`. 1 to 10 lowercase letters and digits; the default is CDK's own, `hnb659fds`, so a configuration without it synthesizes what it did before. It must be the qualifier the account was bootstrapped with and the `Qualifier` the Deploy boundary was rendered with. Tests: the synthesized stack and its asset manifest carry the qualifier; the schema accepts only the CDK shape.
- README: "Permissions boundaries" no longer claims that plain `cdk bootstrap --custom-permissions-boundary` bounds the bootstrap roles. Bootstrapping is the estate's job (the roles must all carry the Deploy boundary, qualifier matching `cdk.qualifier`); the README says what is required, with a generic example.

## boundary/v0.2.1

- **Fix: the Deploy boundary lets CloudFormation create the API Gateway service-linked role.** A custom domain with mutual TLS (`AWS::ApiGateway::DomainName`) makes API Gateway create `AWSServiceRoleForAPIGateway` (service `ops.apigateway.amazonaws.com`) the first time one exists in an account; with only the ECS and CodeStar Notifications roles allowed, the first deploy into a fresh account failed there with "Caller does not have permissions to create a Service Linked Role". The allow-list is now `codestar-notifications`, `ecs` and `ops.apigateway`, each with the resource type that needs it in a comment; the audit of the synthesized stack found no other type that creates one.
- `iam:CreateServiceLinkedRole` is now scoped to `role/aws-service-role/*` instead of every resource, still only for the listed `iam:AWSServiceName` values. The size grows by about 100 characters, well inside `MaxComponentSize`.
- **Drift guard for service-linked roles.** `Coverage` gains `ServiceLinkedRoles` (read from the rendered document) and `NeedsServiceLinkedRole` (a table in the package of the resource types that create a service-linked role, and its service). `cdk/test/boundary-drift.test.ts` fails when a resource type of the synthesized stack needs a role the boundary does not allow, so the next such type cannot repeat this at deploy time; a Go test fails on an allowed role that no type in the table needs.

## boundary/v0.2.0

- **Breaking: `Runtime` and `Deploy` return `policy.Document` of `github.com/truvity/aws-structure/policy` (v0.1.0).** The package's own loosely typed `Document` and `Statement` (their fields were `any`) are gone, and with them `Document.JSON()`: marshal with `json.Marshal`, which is canonical, minified and the same bytes as before. `Document.Size()` is now `policy.Document.Size()`, and `Validate()` is new. The module's only dependency is the policy module, which has none of its own; the package still has no AWS SDK or infrastructure-tool dependency.
- The documents are byte for byte what v0.1.0 rendered: the golden files are untouched, and the test that `Runtime` plus the estate's two guards equals the earlier tool's document still passes. `MaxComponentSize`, `GuardReserve`, `MaxSize`, `DeployCoverage` and the drift guard are unchanged. A new test validates both documents.

## boundary/v0.1.0

- Add `github.com/truvity/grun/boundary`, a standard-library-only Go module that
  renders the stack's IAM permissions boundaries from parameters:
  `Runtime` (the stack's own roles; the document an earlier tool rendered,
  moved unchanged, minus the estate guards the caller appends) and
  `Deploy` (the CDK bootstrap roles: an allow list that can create the stack's
  resources and the roles bounded by the Runtime boundary, and nothing more in
  IAM). `DeployCoverage` reports the services and CloudFormation resource types
  the Deploy boundary covers.
- Each document is held to 5,000 characters minified, leaving room under IAM's
  6,144 for the caller's guards; the constructors return an error beyond it.
- Add a drift guard: `just boundary-coverage` writes the Deploy boundary's
  coverage and `cdk/test/boundary-drift.test.ts` fails when the synthesised
  stack has a resource type the boundary does not cover.
- README: "Permissions boundaries".
